# Autonomous release worker (Windows)

`python tools/release_worker.py --start --version 1.9.1` launches a detached, hidden process that does not use Codex, a model, API credits or chat limits. Requires the existing GitHub CLI login with repository write access, Git, Git Bash, Python 3.12+, Node, OSS CAD Suite and the RISC-V GCC configured in `fw/build.sh`. The PC must remain powered on, awake and connected to the internet.

Check progress with `python tools/release_worker.py --status --version 1.9.1`. Status, PID, logs and pinned source SHA are under `build/release-worker/1.9.1/`. A process lock prevents duplicate workers. After a process exits or a PC restart, the same start command resumes the same pinned source and reuses verified placements. There is no automatic startup at Windows sign-in.

The worker snapshots `origin/main` through `git archive` into its own directory. It never builds from a changing checkout, edits feature defines to make Full smaller, or uses an older bitstream. It runs the printer regression and web tests, builds firmware and independently builds Full and Minimal. Placement attempts have a 20-minute timeout and try different seeds/control-set algorithms without dropping features. Release placement runs without `--timing-allow-fail` and the last timing result for every reported clock must pass. Exhausted attempts stop with `failed` in `status.json`; arbitrary RTL bugs cannot be repaired automatically by this script.

Only after both bitstreams pass does it prepare a draft GitHub release, upload firmware, Full/Minimal binaries, web archive, timing reports and a source/hash manifest. It downloads the assets again and compares SHA256 before publishing the draft as latest. An existing tag for another commit is never overwritten. It dispatches the existing desktop installer workflow separately; native installer completion is not a prerequisite for the firmware/FPGA release. Existing native apps remain compatible. Physical hardware testing is explicitly not claimed.

To stop it, use the exact PID in `status.json` and terminate that process tree; do not kill all Python/nextpnr processes, since other projects may be building. Keep source and logs for diagnosis. Fixing a failed build and changing the pinned commit requires an explicit new build directory/version; the script does not silently change its release sources.
